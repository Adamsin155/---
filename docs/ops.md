## 1. פונקציות Edge

`create-quote` (עם `verify_jwt=true`) מתוארת כאן. `staff-admin` ו־`reminders` רצות עם `verify_jwt=false` ובודקות את הקורא בקוד; `reminders` מתוארת בסעיף 10. היא מחשבת את המחיר מחדש בשרת עם אותו מנוע תמחור שהדפדפן משתמש בו.

**הקבצים שנפרסים יחד:**

| קובץ | מה זה |
|---|---|
| `supabase/functions/create-quote/index.ts` | הפונקציה |
| `supabase/functions/_shared/app/pricing.js` | עותק של `app/pricing.js` |
| `supabase/functions/_shared/app/catalog.js` | עותק של `app/catalog.js` |
| `supabase/functions/_shared/app/legal.js` | עותק של `app/legal.js` |

- העותקים ב־`_shared/app/` נוצרים בסקריפט, והפונקציה מייבאת רק אותם (`../_shared/app/pricing.js`). כך היא לא תלויה במאגר ציבורי.

- `node scripts/sync-functions.mjs --check` נכשל אם עותק חסר, ישן או מיותר. ה־CI מריץ אותו בכל דחיפה, וגם `npm test` בודק את זה (`tests/sync-functions.test.mjs`).
- פונקציה חדשה שצריכה מודול מ־`app/`, למשל מנוע הפרוטוקול לתזכורות: מוסיפים אותו ל־`ENTRIES` בסקריפט, מריצים, ומייבאים מ־`../_shared/app/…`.

**פריסה:**

2. אחת משתי הדרכים:

## 2. פרסום האתר (GitHub Pages)

האתר מוגש מהענף `gh-pages`. **כל קובץ בענף הזה ציבורי** לכל מי שמגיע לנתיב שלו, גם כשהמאגר פרטי. לכן מפרסמים רק את קבצי האתר:

- **מתפרסם:** דפי ה־HTML שבשורש (`index.html`, ‏`q.html`, ‏`quotes.html`, ‏`client.html`, ‏`clients.html`), ‏`clients.webmanifest`, התיקיות `app/` ו־`payouts/`, ‏`.nojekyll`, ו־`CNAME` כשהוא קיים.
- **לא מתפרסם:** `docs/`, ‏`supabase/`, ‏`tests/`, ‏`scripts/`, ‏`.claude/`, ‏`.github/`, ‏`README.md` ו־`package*.json`. הרשימה נקבעת ב־`scripts/build-pages.mjs`.
- `app/` ציבורי מעצם טבעו, כי הדפדפן מריץ אותו. זה כולל את `pricing.js`, ‏`catalog.js` ו־`legal.js`. לכן לא שמים ב־`app/` שום דבר שאסור שיראו.

**איך מפרסמים:** עומדים על הענף שרוצים לפרסם. מתפרסם רק מה שנשמר ב־commit.

```bash
git fetch origin gh-pages
node scripts/build-pages.mjs --commit
```

- הסקריפט יוצר commit שיש בו רק את קבצי האתר, מעל `origin/gh-pages`. הוא מדפיס את פקודת הדחיפה, `git push origin <sha>:refs/heads/gh-pages`, ולא דוחף בעצמו. אם הדחיפה נדחית, מריצים שוב את שתי הפקודות.
- **לא** מפרסמים יותר ב־`git push origin <ענף>:gh-pages`. הפקודה הזו מפרסמת את כל המאגר.
- תצוגה מקדימה: `node scripts/build-pages.mjs /tmp/pages`, ומגישים את התיקייה. ה־CI מריץ את בדיקות הדפדפן מול תיקייה כזו, כך שקובץ שהאתר צריך ולא מתפרסם נתפס שם.
- דף HTML חדש בשורש מתפרסם לבד. תיקייה חדשה שהאתר טוען מוסיפים ל־`DIRS` בסקריפט. `tests/build-pages.test.mjs` נכשל אם דף מפנה לקובץ שלא מתפרסם.
- בדיקה אחרי הפרסום: האתר עובד, ו־`https://adamsin155.github.io/---/docs/ops.md` מחזיר 404.
- הפרסומים הקודמים, עם כל המאגר, נשארים בהיסטוריה של `gh-pages`. ‏Pages מגיש רק את ה־commit האחרון, וכשהמאגר פרטי גם ההיסטוריה פרטית.

## 3. סודות ומשתני סביבה (שמות בלבד)

`create-quote` קוראת:

| משתנה | בשביל מה |
|---|---|
| `SUPABASE_URL` | כתובת הפרויקט |
| `SUPABASE_ANON_KEY` (מפתח ישן, JWT) | לקוח Supabase בשם המשתמש שקרא: `auth.getUser()` ו־`rpc('is_staff')` |
| `SUPABASE_SERVICE_ROLE_KEY` (מפתח ישן, JWT) | שמירת ההצעה בטבלה `quotes`, עוקף RLS |
| הכותרת `Authorization` של הבקשה | ה־JWT של איש הצוות המחובר |

- את כל המשתנים האלה Supabase מזריקה לבד. אין סודות שהגדרנו ביד. אם יתווספו (למשל ספק מייל), מגדירים אותם ב־Edge Functions → Secrets או ב־`supabase secrets set`, ולעולם לא בקובץ במאגר.
- המפתחות החדשים זמינים לפונקציות כ־`SUPABASE_PUBLISHABLE_KEYS` ו־`SUPABASE_SECRET_KEYS`: אובייקט JSON, והמפתח הראשי נמצא תחת `default`.
- בדפדפן: `app/supa.js` מחזיק את כתובת הפרויקט ואת המפתח הציבורי `sb_publishable_…`. הוא ציבורי מעצם הגדרתו. ההגנה היא RLS.
- מחוץ למאגר: טוקן הגישה של ה־CLI (`SUPABASE_ACCESS_TOKEN`) וסיסמת מסד הנתונים. הם אישיים ונשמרים רק בלוח הבקרה ובמחשב של מי שפורס.

## 4. מעבר למפתחות החדשים: עד 31.12.2026

לפי Supabase, המפתחות הישנים `anon` ו־`service_role`, שמבוססים על JWT, עובדים עד סוף 2026. האתר כבר משתמש ב־`sb_publishable_`, ורק `create-quote` עוד תלויה במפתחות הישנים. היעד שלנו הוא להשלים את המעבר עד 1.12.2026, כדי להשאיר מרווח.

1. Settings → API Keys: מוודאים שיש מפתח publishable ומפתח secret בשם `default`.
2. ב־`create-quote`:
   - במקום `SUPABASE_ANON_KEY` קוראים `JSON.parse(Deno.env.get('SUPABASE_PUBLISHABLE_KEYS')!).default`.
   - במקום `SUPABASE_SERVICE_ROLE_KEY` קוראים `JSON.parse(Deno.env.get('SUPABASE_SECRET_KEYS')!).default`.
   - ה־JWT של המשתמש ממשיך לעבור בכותרת `Authorization`, כמו היום.
3. `verify_jwt` המובנה מבין רק JWT. אם עוברים גם למפתחות חתימה חדשים (JWT signing keys), או שפונקציה נקראת עם מפתח `sb_secret_`, מגדירים לה `verify_jwt=false` ובודקים בקוד. `create-quote` כבר בודקת בעצמה (`getUser` מחזיר 401, ו־`is_staff` מחזיר 403).
4. קריאות מ־`pg_net` ומהתזמון לפונקציות: שולחים את מפתח ה־secret בכותרת `apikey`, לא ב־`Authorization`. את המפתח שומרים ב־Vault, לא בטקסט של ה־SQL.
5. כשכלום כבר לא משתמש במפתחות הישנים, מכבים אותם ב־Settings → API Keys. אפשר להדליק אותם שוב אם משהו נשבר.

## 5. מיגרציות

- כל שינוי במסד הוא קובץ חדש: `supabase/migrations/<YYYYMMDDHHMMSS>_<שם>.sql`, עם חותמת זמן מאוחרת מהקובץ האחרון. **לא עורכים מיגרציה שכבר הוחלה**; מתקנים בקובץ חדש.
- מי שמחזיק את הגישה ל־Supabase מחיל אותן, לפי הסדר:
  - בודקים מה כבר הוחל: `list_migrations` ב־MCP, או Database → Migrations.
  - מחילים כל קובץ חסר עם `apply_migration` ב־MCP. השם הוא שם הקובץ בלי החותמת ובלי `.sql`, למשל `drop_set_my_person`.
  - אחרי זה מריצים `get_advisors` (אבטחה) ואת הבדיקות.
- ההיסטוריה במסד נשמרת לפי שעת ההחלה, ולא לפי החותמת שבשם הקובץ. לכן לא משתמשים ב־`supabase db push` בלי ליישר קודם את ההיסטוריה (`supabase migration repair`), כי אחרת הוא ינסה להריץ הכול מחדש.
- `npm test` מריץ את כל המיגרציות, לפי הסדר, על Postgres אמיתי שרץ בתוך Node ‏(PGlite, ‏`tests/sql/`). מיגרציה שלא נטענת מכשילה את הבדיקות עם שם הקובץ. מה ש־Supabase מספקת והבדיקות צריכות (התפקידים `anon`/`authenticated`, ‏`auth.jwt()`, ‏Vault, ‏cron ו־net) נמצא בגרסה מינימלית ב־`tests/sql/supabase-stub.sql`. אם מיגרציה חדשה צריכה משהו שחסר שם, מוסיפים אותו לשם (או ל־`SKIP` ב־`tests/sql/pg.mjs`), עם שורה שמסבירה למה.

## 8. כתובת קבועה: `app.astrateg.com`

1. **DNS**, אצל רשם הדומיין: רשומת `CNAME` בשם `app` שמצביעה על `adamsin155.github.io` (בלי שם המאגר ובלי נתיב).

   - Site URL: ‏`https://app.astrateg.com/`
   - Redirect URLs: מוסיפים `https://app.astrateg.com/quotes.html` ו־`https://app.astrateg.com/payouts/`

## 10. מנוע התזכורות

*שלב 3 ([התוכנית, עיקרון 4 וסעיף 5](plan/system-plan.md), החלטות 7–24). הכללים עצמם הם נתונים ב־`app/reminder-rules.js`; ההרצה ב־`app/reminder-engine.js`.*

**איך זה עובד:** בכל דקה `pg_cron` מריץ את `public.reminders_tick()`, שקוראת לפונקציה `reminders` עם סוד מה־Vault. הפונקציה טוענת את הלקוחות, הסימונים והמשימות (במפתח השירות), מחשבת בשעון ישראל אילו שלבים בסולמות הגיעו, ורושמת כל שלב ב־`public.reminder_log` עם מפתח ייחודי. לכן כל שלב יוצא פעם אחת, גם כששתי הרצות חופפות. אחר כך היא שולחת Web Push לטלפונים שב־`public.push_subscriptions`.

- **הרצה שנעצרה באמצע:** התראה לטלפון נרשמת קודם כ־`pending`, והופכת ל־`sent` או `failed` רק אחרי שהשליחה נענתה. הרצה שנעצרה בין השניים (timeout, עצירת ה־worker) משאירה אותה `pending`. אחרי 10 דקות הרצה אחרת לוקחת אותה (`public.reminders_reclaim`, פעולה אחת, כך ששתי הרצות לא לוקחות אותה יחד), בודקת שהיא עדיין נכונה ושולחת. מה שלא נשלח תוך שעתיים (או אחרי 3 ניסיונות) נרשם `failed` עם `lost`, ולא נשלח באיחור.
- **שורה שהמסד דוחה** (למשל טקסט ארוך מדי) לא עוצרת את ההרצה: הטקסט נחתך לאורך העמודה, ושורה שעדיין נדחית נספרת ב־`rejected` ונשארת לדקה הבאה.

- **רמות:** צלצול (פוש), שקט (רק ב"התראות" במערכת), שורה בתקציר, ולוח הבעלים.

```sql
from public.reminder_log where created_at > now() - interval '1 day' order by id desc;
-- צלצולים לאדם ביום (מול היעדים שבסעיף 5 בתוכנית)
select person, (created_at at time zone 'Asia/Jerusalem')::date as day, count(*)
from public.reminder_log where level = 'ring' and channel = 'push' and status = 'sent' and not exempt group by 1, 2 order by 2 desc, 1;
-- תקלות שליחה ומכשירים בעייתיים
select created_at, person, title, reason from public.reminder_log where status = 'failed' order by id desc limit 20;
select email, fail_count, last_error, last_ok_at from public.push_subscriptions where fail_count > 0;
```
- מכשיר שה־push service מחזיר עליו 404 או 410 נמחק לבד. כל תקלה אחרת נרשמת בשורה (`failed`) ובמכשיר (`fail_count`, ‏`last_error`).
- שורות תקועות: `select id, key, claimed_at, attempts from public.reminder_log where status = 'pending' and claimed_at < now() - interval '10 minutes';` (אמור להיות ריק, חוץ מרגע אחרי הרצה שנעצרה).
- `reminder_runs` נשמר 14 יום, `cron.job_run_details` שבוע.

**אבטחה:**
- המפתח הפרטי של VAPID וסוד ה־cron נמצאים רק ב־Vault. רק פונקציות של `service_role` קוראות אותם (`reminders_vapid`, ‏`reminders_check_secret`), וסוד ה־cron נבדק בתוך מסד הנתונים.

**מה נבנה:**
- **מסך הסכמה חד־פעמי** בכל עמוד של הצוות (`app/whatsapp.js`, מתוך `mountSession`), רק כשהמתג דולק: הנוסח המדויק מגיע מהמסד לפי גרסה, עם המספר של האדם עצמו, שני כפתורים זהים (וואטסאפ, או "רק התראות באפליקציה") וקישור להודעת הפרטיות לעובדים. סגירה בלי בחירה = "אחר כך" לאותה לשונית. ב"מה עליי" יש כרטיס "הודעות ב־WhatsApp": מצב, הפסקה בכל רגע, והסכמה מחדש.
- **מה נשמר כראיה** (`whatsapp_consent_log`): הבחירה, הכפתור שנלחץ, הנוסח המלא כפי שהוצג (עם המספר), הגרסה, המספר, המועד בשעון השרת, הדפדפן, וגם ביטול: מתי ובאיזה ערוץ (`app` או `whatsapp`). כל אחד קורא רק את שלו. המשרד רואה מי הסכים דרך `whatsapp_team_status()`, בלי מספרים.

- **שליחה** (בתוך `reminders`, לא פונקציה נפרדת): כל צלצול וכל תקציר שההרצה כבר שולחת בפוש יוצאים גם כתבנית וואטסאפ, למי שהסכים. וואטסאפ לא מוסיף שום הודעה: שעות השליחה, התקרה, מצב יום הצילום והמפתח הייחודי של היומן כבר בחרו את השורות. `whatsapp_messages` מחזיקה שורה אחת לכל שורת יומן (`log_id` ייחודי), כך שהרצה חוזרת לא שולחת פעמיים. **בשעות ההסכמה בלבד:** א׳–ה׳ 08:30–19:00, בערב חג עד 13:00. צלצול של יום צילום מחוץ לשעות (התדריך ב־17:00 עובר, אבל הבדיקה של 20:00 לא) יוצא בפוש בלבד.

  הפריטים של פעם בתקופה (לפי `clients.deliverables`) מתפזרים שווה על חודשי המחזור, באמצע החלק של כל אחד. "מה עליי" מציג את הפריטים של החודש הנוכחי, ואת מה שבחודש הבא צריך לקרות לפני שהוא מתחיל (התכנון של עילאי), מ־7 ימים לפני. חודשים שעברו מופיעים רק ב־`year.html`.
- **הסימונים:** טבלה חדשה `public.client_month_marks` (לקוח, חודש, פריט: `plan`, ‏`posted`, ‏`report`, ‏`photo`, ‏`photoshot`, או `ch14.1`, ‏`collab.2`, ‏`story.1`, ‏`round.1`). לא השתמשתי ב־`protocol_checks`: המפתחות שלה חייבים להתחיל ב־`pNN.`, וזה לא תהליך בפרוטוקול. רק המשרד (`is_office()`, כולל עילאי) קורא וכותב; מי ומתי נחתמים במסד. הבעלים, עירית, ליאור ואופיר מסמנים גם בשם אחר, ונרשם "בשם" (החלטה 23); עילאי רק את שלו.
- **תזכורות, בעדינות:** שורת תקציר ב־08:30 ביום הראשון של כל חודש לכל מי שיש לו בו פריטים (`monthStart`); צלצול אחד ביום לכל אדם ב־10:00, על כל הפריטים שלו שמועדם היום (`monthDay`); ושורת תקציר "באיחור" בבוקר יום העסקים שאחרי המועד (`monthLate`). בלי הסלמה. לשורות האלה אין `ref` (הבדיקה של `reminder_log.ref` מקבלת רק מפתחות תהליך).

**גרסאות הפרוטוקול ללקוח.** `clients.protocol_version` (העמודה הייתה קיימת עם ברירת מחדל 1 שאיש לא קבע) היא הגרסה שבה הלקוח התחיל. המסד חותם אותה בהוספה, ולא משנה אותה בעדכון מהדפדפן; רק SQL Editor או מפתח השירות. ללקוח שהתחיל בגרסה קודמת:
- פריט שנוסף אחר כך מסומן בכרטיס "חדש בפרוטוקול (גרסה N) · לא נספר באיחור". הוא נשאר עבודה פתוחה (ב"מה עליי" ובהשלמת התהליך), אבל תהליך לא נחשב באיחור בגללו. בחרתי לא להפוך אותו ל"אם רלוונטי" כדי שתהליך שכולו חדש (למשל שיוך העורך, 22א, ללקוח מגרסה 1) לא ייעלם מהעבודה.
- מועד שגרסה מאוחרת קיצרה נשאר כמו שהתחיל: למשל התסריטים, יום עסקים 3 ללקוח מגרסה 4 ויום 2 מגרסה 5 (החלטה 14). בפועל המועד הוא המאוחר מבין השניים.
- מה השתנה בכל גרסה נמצא ב־`PROTOCOL_HISTORY` ומוצג ב־`year.html`. בהעלאת גרסה: מוסיפים שם את הגרסה עם הפריטים החדשים ומועדים שהשתנו, ומעלים במיגרציה את `private.protocol_version_current()` ואת ברירת המחדל של העמודה. הבדיקות נכשלות עד שכל אלה מסכימים.
- **לקוחות קיימים:** המיגרציה קובעת לכל לקוח שעדיין על 1 את הגרסה לפי מתי נפתח, מול מתי כל גרסה הגיעה לענף הראשי (v2 ב־13:27, v3 ב־14:04, v4 ב־16:00 UTC ב־29.9), ולא יותר מ־4. כלומר כל הלקוחות שקיימים היום נקראים כגרסה 4 ומטה, גם מי שנפתח אחרי שגרסה 5 נכתבה ועד שהמיגרציה הוחלה (הוא מקבל את מועד התסריטים הישן, המקל). המסכים קוראים שורה שעדיין על 1 באותו כלל, כך שהם מסכימים גם לפני ההחלה. שינוי ידני: `update public.clients set protocol_version = 5 where id = '<id>';` ב־SQL Editor.

**חידושים: רשימת 90 הימים (תחנה 8, תהליכים 34–35).** בעמוד, לבעלים, לליאור ולעירית: לקוחות פעילים שהחבילה שלהם מסתיימת בתוך 90 יום, לפי התאריך. לכל אחד שלב תהליך 34 וסיכום תוצאות ממה שכבר במערכת: תוצרים מול החבילה (כמו בקצב שבמסך הבעלים), ימי צילום שהתקיימו, אחוז התהליכים שנסגרו בזמן (בלי היסטוריה מיובאת), המחזור החודשי, ושביעות רצון.
- **שביעות רצון:** מ־`client_surveys` של דף המצב (סעיף 13; הצורה ב־`app/surveys.js`): `kind` ‏`shoot` ו־`delivery` בסולם 1–5, ו־`nps` בסולם 0–10, עם `at`. `app/year-data.js` (`loadSurveys`) קורא רק `client_id, kind, score, source, at` (לא את שם העונה), ו־`surveySummary` ב־`app/renewals.js` מסכם: ממוצע ה־1–5, וההמלצה בנפרד; אזהרה על 2 ומטה מ־5 או 4 ומטה מ־10 (הספים של המסד). אם הטבלה לא נקראת, הרשימה לא נכשלת.
- **"הצעת חידוש":** פותח את בונה ההצעות (`index.html`) עם טיוטה ממולאת: החבילה, התוספות וההנחה מההסכם החתום (`quotes.model.selection`), ושם הלקוח ופרטיו מההסכם; בלקוח שנפתח ידנית, מתוך שם החבילה וסוג הצילום. זו הטיוטה שהבונה כבר שומר בלשונית (`sessionStorage`, `astrateg-draft`), ולכן אין שינוי בבונה. טיוטה אחרת בלשונית מוחלפת רק באישור.
- **ההודעה ללקוח ידנית.** הצעת חידוש היא פרסומת לפי חוק הספאם (סעיף 7 בתוכנית), ולכן שום דבר כאן לא שולח. העמוד אומר את זה ליד הרשימה.
- **תזכורות (`renewalList`):** שורת תקציר לליאור ולבעלים 90 יום לפני; לבעלים 60 יום לפני (לליאור כבר יש שורה מהכלל `renewal`, 75/60/45); צלצול אחד לליאור ב־12:00 ביום של תהליך 34 (60 יום לפני, או יום העסקים שלפניו) אם אף פריט שלו לא סומן והוא לא ממתין ללקוח; ו־30 יום לפני שורה לליאור, ולבעלים רק אם כבר נרשמה שיחת חידוש (אחרת הכלל `renewal` מצלצל לו מיד, מקרה 4). נעצר כשתהליך 34 הושלם או כשהלקוח כבר לא פעיל.

## 16. שלב 6: היומן האישי והתובנות

*[התוכנית, שלב 6](plan/system-plan.md). היומן נבנה בלי ה־API של גוגל, כי החלטה 32 (Google Workspace) עוד פתוחה: קישור מנוי ‏(iCalendar) שכל יומן קורא, Google, ‏Apple ו־Outlook.*

**"היומן שלי"** (כרטיס ב"מה עליי", `app/calendar-card.js`):

## 18. הקשחה אחרי הבדיקה של שלבים 4–6

*המיגרציה `20260930210000_hardening.sql` (אחרי `20260930200000_calendar_feeds.sql`, בטוחה להרצה חוזרת, לא מזיזה נתונים). הבדיקות: `tests/sql/hardening.test.mjs`, `tests/protocol-writers.test.mjs`, והצורה החדשה של `clients` בכל בדיקות הדפדפן (`tests/fake-clients.mjs`).*

**1. העמודות של המשרד בכרטיס הלקוח.** RLS בוחר שורות, לא עמודות: עד עכשיו עורך, ניראל או אלי יכלו לבקש ישירות מהמסד את `clients.phone`, `clients.notes` ו־`clients.closed_reason` של כל לקוח שהם רואים.
- `authenticated` רשאי לקרוא מ־`public.clients` את כל העמודות **חוץ** משלוש האלה (הרשאה לפי עמודה). `select *` נדחה לכולם, גם למשרד. אין העברת נתונים: הכול נשאר במקום, ולכן אין סיכון לנתונים בהחלה.
- המשרד (הבעלים, עירית, ליאור, אופיר ועילאי, `is_office()`) קורא אותן דרך `public.clients_private(p_ids)` (security definer; לכל אחד אחר היא מחזירה אפס שורות). הכתיבה לא השתנתה (עדכון והוספה של המשרד).
- **בדפדפן:** `app/protocol-data.js` קורא את העמודות הרגילות ומוסיף את שלוש העמודות מ־`clients_private` (ריק מחוץ למשרד, ולכן `null`). כל עמודי המשרד מתנהגים כמו קודם. עורך שפותח כרטיס כבר לא רואה את ההערות של המשרד ואת סיבת הביטול (קודם הן הוצגו לו). לפני ההחלה הפונקציה חסרה, והקוד קורא את העמודות מהטבלה כמו קודם, ולכן **מפרסמים את האתר קודם, ורק אז מחילים את המיגרציה**: הדפים הישנים מבקשים את הטלפון ישירות, ואחרי ההחלה המסד דוחה את הבקשה והרשימות לא נטענות, לכולם.
- **עמודה חדשה ב־`clients`** צריכה `grant select (עמודה) on public.clients to authenticated` באותה מיגרציה (או להיכנס לרשימת העמודות של המשרד). `tests/sql/hardening.test.mjs` נכשל על עמודה שלא סווגה.
- **הצעות המחיר** (`public.quotes`, עם הטלפון של הלקוח והמחירים): קריאה למשרד בלבד. הבונה וההצעות שנשלחו הם של המשרד; הלקוח ממשיך לקרוא ולחתום דרך `get_quote` ו־`sign_quote`.

**2. מי מסמן איזה פריט בפרוטוקול.** עד עכשיו כל מי שרואה לקוח יכול היה לכתוב כל סימון שלו (למשל עורך מסמן `p25.approved` או `p27.toilai`, או מוחק את `p25.return.1` של אופיר).
- הכלל הוא מה שהאפליקציה עצמה מאפשרת: הבעלים, עירית, ליאור ואופיר (`SCOPE` 'office') כותבים הכול, כמו היום. עילאי, אלי והעורכים כותבים רק: פריט שלהם (בעלי הפריט, או בעלי התהליך; "עורך" הוא העורך של אותו צילום, של הלקוח או של הסבב, בלי נפילה לעורך הראשי); "אני על זה" בתהליך עם שני בעלים שהם מהם; המתנה ללקוח היכן שהכרטיס (`CLIENT_PROCS`) או עמוד העורך (`BLOCKS`) מציעים אותה להם; עצירת עריכה (העורך של הצילום, או כל עורך כשאין שיוך); העברה (`handoff`) מתהליך שיש להם בו פריט; "תוקן" על החזרה של אופיר (`p25.fixed.N`: העורך, `p23.fixed.N`: עילאי); `p17b.brollq` (אלי), `p22.missing` ו־`p27.fixed` (העורך); ו"לדחות…" על תזכורת (`pNN.snooze`) בכל לקוח שהם רואים, כמו קודם. כל השאר (ההחזרות של אופיר, ההחלטות של ליאור, מצב יום צילום, מועד הזום, "הלקוח ענה"…) של המשרד.
- **היסטוריה מיובאת** (הערה 'ייבוא'): רק המשרד כותב אותה (כשהוא פותח לקוח). מי שהפריט שלו יכול לסמן מחדש או לנקות פריט מיובא שלו.
- **איפה:** הטבלה `private.protocol_writers` נוצרת מ־`app/protocol.js` בידי `node scripts/protocol-writers.mjs` (הבלוק בין `-- protocol-writers:begin` ל־`end` במיגרציה). `private.protocol_write_ok()` מחליטה, והמדיניות של `protocol_checks` נחלקה לקריאה (כמו קודם) ולהוספה, שינוי ומחיקה שבודקים אותה. `mayWrite()` בסקריפט היא אותו כלל ב־JavaScript, והבדיקה משווה את שתיהן לכל אדם, מפתח וסבב.
- **שינוי בפרוטוקול** (פריט חדש, בעלים אחרים): מריצים `node scripts/protocol-writers.mjs` ומכניסים את הפלט למיגרציה חדשה. `npm test` נכשל עד שעושים את זה. סימון חדש שעמוד כותב (לא פריט) נכנס ל־`EXTRA_MARKS` בסקריפט, או לרשימת המשרד בבדיקה.
- **מה לא נבדק כאן:** דף המצב (`approve_item`, `request_fix`), התשובות ב־WhatsApp (`whatsapp_apply`), פתיחת לקוח בחתימה ופונקציות השרת כותבים דרך security definer ובודקים את הקלט שלהם בעצמם.
- **המחזור החודשי:** עילאי מסמן רק את הפריטים שלו (`plan`, `posted`; `private.month_write_ok`). שאר המשרד מסמן כל פריט, גם בשם אחר (החלטה 23).
- סימון שנדחה מגיע לדפדפן כשגיאת הרשאה ("הסימון לא נשמר ולכן בוטל"). מחיקה שנדחית לא מוחקת כלום (0 שורות).

**3. דף המצב.**
- `approve_item` ו־`request_fix` נועלים את שורת הלקוח: שתי לחיצות באותו רגע נרשמות פעם אחת (בקשת תיקון כפולה הייתה פותחת שתי משימות ומצלצלת פעמיים).

## 19. כתיבת תסריטים (תהליך 12) וקישור לשיתוף

*המסך: `scripts.html` (`app/scripts.js`; הכללים `app/scripts-logic.js`; הנתונים `app/scripts-data.js`). הדף לשיתוף: `scripts-view.html` (`app/scripts-view.js`). המיגרציה: `20261003120000_scripts.sql` (אחרי `20260930210000_hardening.sql`, בטוחה להרצה חוזרת, לא נוגעת בנתונים קיימים).*

- **מי:** ליאור והבעלים (`can_manage_scripts()`) תמיד. ליאור (או הבעלים) פותח גישה לעובד נוסף לפי לקוח (`script_grants`, דרך `scripts_grant`), והעובד מקבל קישור בוואטסאפ. אף אחד אחר, גם לא שאר המשרד, לא קורא את התסריטים (RLS על `client_scripts`). גישה לתסריטים לא פותחת את הלקוח עצמו, את הכספת או את הסימונים. "אושר" מסמנים רק ליאור והבעלים (הטריגר `client_scripts_stamp`).
- **כמה תסריטים:** כמות הסרטונים בחבילה (`clients.deliverables.videos`, דרך `scripts_client`), ולא פחות ממה שכבר נכתב. אפשר להוסיף תסריט מעבר לחבילה; בסבב צילום נוסף מוסיפים אחד אחד.
- **שמירה:** כל תסריט נשמר לבד כשמפסיקים להקליד, עם "נשמר · שעה". עד שהמסד מאשר, הטקסט שמור גם בטלפון (`localStorage`). כשאין רשת השמירה מנסה שוב (3, 10, ואז כל 30 שניות, ומיד כשהרשת חוזרת), וטיוטה שלא נשמרה משוחזרת בפתיחה הבאה. לכל תסריט גרסה (`version`): שמירה ממכשיר אחר בינתיים לא נדרסת, והמסך שואל מה לשמור.
- **הפרוטוקול:** כשכל התסריטים "מוכן", המסך מציע לסמן `p12.scripts` ו־`p12.numbered` (אחרי שיחת הדגשים, `p12a.call`). "להשתמש בו כקישור התסריטים של הלקוח" שומר את הקישור לשיתוף ב־`clients.links.scripts` ומסמן `p12.docs`, כך שדף המצב מציג את התסריטים לאישור. **האישור של הלקוח נשאר `approve_item` בדף המצב**; כשנרשם `p13.approved` (שם, או בידי ליאור), התסריטים במצב "מוכן" של אותו סבב עוברים ל"אושר" (הטריגר `client_scripts_on_approval`). טיוטות נשארות טיוטות.
- **הקישור לשיתוף:** כמו הקישור של דף המצב: 32 בתים אקראיים, בטבלה (`script_share_links`) רק טביעת SHA-256, הטוקן ב־Vault (`scripts_link:<id>`), תוקף 180 יום, קישור חדש מבטל את הקודם, וטוקן שבוטל נמחק מ־Vault. הדף האנונימי קורא רק `get_scripts(token)`: שם העסק והתסריטים שיש בהם טקסט, עם הקישורים (http/https בלבד). בלי טלפון, הערות, אנשים או מועדים. לקוח שהסתיים: הדף לא נפתח.
- **סיכום דגשים לקוח:** שדה טקסט חופשי (`content_briefs.fields.summary`) בראש טופס הדגשים ב־`intake.html#focus`, יחד עם 10 הנושאים של 12א. מגיעים אליו מראש דף התסריטים, מהזום ב"תסריטים וזום", ומהאפיון. הוא מוצג ראשון בכל מקום שהדגשים מוצגים: ליד הכתיבה, בכרטיס הלקוח ובעמוד העורך. לא מסמן שום פריט.
- **להחלה:** פרסום האתר, ואז המיגרציה ב־SQL Editor (או `apply_migration` בשם `scripts`). אין פונקציות Edge ואין סודות חדשים. לפני ההחלה הדף אומר "כתיבת התסריטים עוד לא הוקמה".
- **בדיקה אחרי ההחלה:**

  ```sql
  select client_id, person, granted_by, at from public.script_grants;
  ```

## 20. תיק לקוח: קבצים, גלריה ללקוח וגרפיקות בדף המצב

*החלטת הבעלים (3.10.2026): כל הקבצים, גם סרטונים, עולים למערכת עצמה (Supabase Storage) ולא כקישורי Drive. המיגרציה: `20261003110000_client_files.sql`. הפונקציה: `supabase/functions/client-media`. בכרטיס: `app/files-ui.js`; הכללים: `app/files-logic.js`; ההעלאה: `app/upload.js`; הגלריה: `gallery.html` (`app/gallery.js`).*

- **איך זה שמור:** דלי פרטי `client-files` (בלי כתובת ציבורית). נתיב כל קובץ: `<client_id>/<kind>/<uuid>-<שם קובץ בטוח>` (שם באותיות לטיניות בלבד, כי Storage לא מקבל עברית בשם). לכל קובץ שורה ב־`public.client_files`: סוג (`logo`, ‏`image`, ‏`video_existing`, ‏`material_other`, ‏`deliverable_graphic`, ‏`deliverable_video`, ‏`deliverable_highlight`, ‏`deliverable_site`, ‏`deliverable_other`), תווית, גודל, `posted_on` (היום שעלה לרשתות, לגאנט השנתי), `link`, מי העלה ומתי, ומחיקה רכה (`deleted_at`). אתר שניתן רק כקישור נשמר כקובץ טקסט קטן עם הקישור (`text/uri-list`), כך שלכל שורה יש קובץ אמיתי.
- **מי:** קוראים את הקבצים כל מי שרואה את הלקוח (`can_see_client`, סעיף 9). מעלים: הבעלים, עירית, ליאור ואופיר כל סוג; עילאי גרפיקות, Highlights ואתר; עורך (נדיה, יריב, אנה, ניראל) רק סרטונים, ורק בלקוח שמשויך אליו. מוחקים: המשרד (בלי עילאי) ומי שהעלה; רק המשרד מחזיר קובץ שנמחק, ורק הוא קורא את הקובץ עצמו אחרי מחיקה. אף אחד לא מוחק שורה. אותם כללים במדיניות של `storage.objects` (התיקייה הראשונה היא הלקוח, השנייה הסוג). את התאריך שעלה לרשתות ואת הקישור משנים מי שמעלה את הסוג, מי שהעלה, המשרד, ועילאי בכל תוצר.
- **גודל:** תמונות (לוגו, תמונות, גרפיקות) עד 20MB; כל השאר עד 2GB. הבדיקה בדפדפן (הודעה בעברית לפני שמשהו נשלח), במסד (`client_files_size`) ובדלי (2GB). **לפני ההחלה:** ב־Storage → Settings מעלים את *Global file size limit* ל־2GB לפחות (ב־Pro ברירת המחדל 50MB, והדלי לא יכול לעבור אותה).
- **העלאה:** עד 6MB בבקשה אחת עם פס התקדמות; מעל זה בפרוטוקול TUS (העלאה שאפשר לחדש) בחלקים של 6MB, כפי ש־Supabase דורשת. ניתוק באמצע ממשיך מהבייט האחרון שהשרת קיבל, ודף שנסגר באמצע ממשיך כשבוחרים שוב את אותו קובץ באותו מכשיר (עד יום). ה־supabase-js שבמאגר לא תומך בזה, ולכן `app/upload.js` כתוב כאן, בלי תלויות.
- **בכרטיס הלקוח:** "תיק לקוח" בשני חלקים, "חומרים מהלקוח" ו"תוצרים", עם ספירה לכל סוג. תצוגה מקדימה נטענת רק כשהתמונה מגיעה למסך, דרך קישור חתום לשעה שנוצר רק אז; סרטון מתנגן בלחיצה. בטופס האפיון (`intake.html#form`) אופיר מעלה לוגו, תמונות וסרטונים מהטלפון בפגישה; תמונה או סרטון מסמנים בטופס "התקבל", ולוגו שהועלה נחשב כמו קישור ללוגו (`p05.logo`, ולא נפתחת לעירית משימה לבקש אותו).
- **הגלריה ללקוח (צפייה בלבד):** עירית, ליאור או הבעלים יוצרים בכרטיס קישור (`gallery_link_create`, שנה), מעתיקים הודעה או פותחים WhatsApp, ומבטלים. אותו מנגנון כמו קישור דף המצב: בטבלה `client_gallery_links` טביעת SHA-256, הטוקן ב־Vault (`gallery_link:<id>`), קישור חדש מבטל את הקודם, וטוקן שבוטל נמחק מ־Vault. נפתח גם ללקוח שהסתיים (התוצרים שלו), לא ללקוח שבוטל. הגלריה מראה רק תוצרים: בלי שמות עובדים, בלי מועדים פנימיים, ושם ההורדה הוא `astrateg-<סוג>-<תאריך>`. **לשים לב:** הקישור החתום לקובץ מכיל את הנתיב, כולל שם הקובץ המקורי (כך Storage חותם). לא לתת לקובצי תוצרים שמות עם הערות פנימיות או שמות של עובדים.
- **הפונקציה `client-media`** (`verify_jwt=false`): `POST { t, scope: 'gallery' | 'status' }`. בודקת את הטוקן במסד (`public.media_for_token`, רק ל־service role), חותמת את הקבצים לשעה (`createSignedUrls`, ולתמונות גם תצוגה מוקטנת), ומחזירה בלי הנתיב. CORS רק לכתובות האתר ול־localhost. כמו `calendar`, לא נרשם כלום מהבקשה, רק קוד שגיאה קצר.
- **דף המצב:** ליד האישור של 9 הגרפיקות הראשונות (תהליך 7) וליד יתרת הגרפיקות (23) הלקוח רואה את הגרפיקות שהועלו: מה שהועלה לפני אישור ה־9 שייך להן, ומה שאחריו ליתרה. `approve_item` ו־`get_status` לא השתנו.
- **עלויות:** Pro כולל 100GB אחסון ו־250GB תעבורה בחודש; מעבר לזה כ־$0.021 ל־GB אחסון וכ־$0.09 ל־GB תעבורה. סרטון סגור של דקה הוא בערך 50–150MB, ולכן התעבורה (הורדות וצפיות של לקוחות) היא מה שכדאי לעקוב אחריו (Usage בלוח הבקרה). התצוגה המוקטנת של תמונות משתמשת ב־Image Transformations: 100 תמונות מקור בחודש כלולות, ואחר כך כ־$5 לכל 1,000. לכבות: `MEDIA_THUMBS=off` בסודות הפונקציה (הגלריה תציג את התמונה עצמה), ובכרטיס התצוגה חוזרת לבד לתמונה המלאה אם ההמרה לא זמינה. הגיבוי היומי של המסד **לא** כולל את הקבצים (סעיף 6).
- **מה לא נמחק לבד:** קובץ של שורה שנמחקה (רכה), וקבצים של לקוח שנמחק מהמסד (השורות נמחקות ב־cascade, הקבצים נשארים). ניקוי, כשיידרש: הבעלים מוחק מ־Storage.
- **הפעלה, בסדר הזה:** (1) Storage → Settings: הגבלת גודל גלובלית 2GB. (2) המיגרציה `20261003110000_client_files.sql` (בטוחה להרצה חוזרת; יוצרת את הדלי, הטבלאות, המדיניות והפונקציות). (3) פריסת `client-media` עם `supabase/functions/_shared/app/files-logic.js` (`node scripts/sync-functions.mjs --deploy` מדפיס את הרשימה). (4) פרסום האתר. אין סודות חדשים (`MEDIA_THUMBS` לא חובה).

## 21. גאנט התוכן ללקוח

*העמוד: `gantt.html?id=<לקוח>` (צוות) ו־`gantt.html?t=<טוקן>` (הלקוח, צפייה בלבד). התבנית: `app/gantt-template.js`; הלוגיקה: `app/gantt-logic.js`; הנתונים: `app/gantt-data.js`; המסך: `app/gantt.js`, `app/styles/gantt.css`. המיגרציות: `20261003130000_content_gantt.sql` ואחריה `20261003130100_gantt_file_fk.sql` (בטוחות להרצה חוזרת).*

**הרעיון.** תבנית אחת קבועה של שנת חוזה, יחסית בלבד (חודש n בחבילה, השבוע והיום בשבוע, יום עסקים, שעה), בלי אף תאריך. מ־`deal_at` ו־`contract_end` של הלקוח נוצרים כל התאריכים, בשעון ישראל, בלי שבת, חג וערב חג (לפרסומים). החודשים וחלוקת הפריטים זהים לשנת החבילה (סעיף 15): הדוח החודשי ביום עסקים 3, התכנון של עילאי ביום העסקים שלפני החודש, וסטורי, קולאבים, ערוץ 14 וימי צילום נוספים באותם חודשים. הכמויות מ־`clients.deliverables`. הכללים במילים מופיעים בעמוד ("איך התבנית בונה את הגאנט").

**שמירה.** `public.client_gantt`: שורה לכל פריט (מפתח מהתבנית כמו `video.7`, ‏`report.3`, ‏`monthly.4.2`; פריט שהוסיפו ידנית: `custom.<n>`), יום (`day`) ושעה בשעון ישראל (`time_il`), סוג, כותרת, מתוכנן / עלה / בוטל, יום העלייה, קישור, קובץ (`file_id` אל `public.client_files.id`, מפתח זר מ־`20261003130100_gantt_file_fk.sql`, אחרי מיגרציית הקבצים; קובץ שנמחק מהטבלה משאיר את הפריט בלי קובץ), הערה פנימית, ו־`edited` כשהתאריך הוזז ידנית (גרירה בלוח או עריכה). "עדכון מהתבנית" מוסיף ומעדכן לפי התבנית, ומשאיר תאריכים שהוזזו ידנית, אלא אם מסמנים במפורש להחזיר אותם. מה שעלה, קישורים, קבצים והערות לא משתנים לעולם; פריט שהתבנית כבר לא יוצרת נמחק רק אם לא נעשה בו דבר.
- **הרשאות:** המשרד (`is_office()`, כולל עילאי שהגאנט שלו) קורא וכותב; כל מי שרואה את הלקוח (`private.my_clients()`: העורך, ניראל בלקוח נטלי, אלי סביב צילום, בעל משימה) קורא בלבד. מי ומתי נחתמים במסד (`protocol_stamp`). התכנון של עילאי ושיחת החידוש תמיד `internal` (המסד קובע).
- **קישור ללקוח:** `public.client_gantt_links`, באותה תבנית כמו דף המצב (סעיף 13): רק hash של הטוקן בטבלה, הטוקן עצמו ב־Vault כדי שהמשרד יעתיק אותו שוב; 400 יום תוקף; קישור חדש מבטל את הקודם, וטוקן שבוטל נמחק מ־Vault. הלקוח קורא רק דרך `public.get_gantt(token)` (anon): העסק, תקופת החוזה והפריטים שאינם פנימיים, עם הקישור של הפריט או של הקובץ; בלי הערות, בלי נתיב קובץ, בלי מי ומתי.
- **קבצים:** אם `public.client_files` קיימת, אפשר לבחור לפריט קובץ של הלקוח (רק של אותו לקוח, המסד בודק), ותמונה מוצגת כתמונה ממוזערת דרך קישור חתום מה־bucket הפרטי `client-files`. עד שהיא קיימת, העמוד אומר שבחירת קובץ תתאפשר בהמשך.
- **קישורים לעמוד:** בכרטיס הלקוח (שורת הקישורים, "גאנט התוכן"), בתהליכים 9, 28 ו־29 בכרטיס וב"מה עליי", ובכרטיסים של עילאי (שלד גאנט, "הגאנט מלא").
- **הדפסה:** "הדפסת החודש" מדפיס את לוח החודש המוצג בעמוד A4 לרוחב, עם הלוגו והמקרא.

**להחלה:** פרסום האתר (סעיף 2: `gantt.html` חדש וקבצים שהשתנו), ואחריו המיגרציה. אין פונקציה לפרוס מחדש ואין סודות חדשים. **בדיקות:** `tests/gantt.test.mjs`, ‏`tests/sql/gantt.test.mjs` (בתוך `npm test`), ו־`tests/gantt-e2e.mjs [תיקיית צילומים]`.

## 22. מבט מנהל: החלפת תצוגה, טבלת הלקוחות, סיכום החוזה, ארכיון ומחיקה

*המיגרציה `20261003140000_manager_features.sql` (אחרי `20260930210000_hardening.sql`, בטוחה להרצה חוזרת). הבדיקות: `tests/sql/manager.test.mjs`, `tests/manager.test.mjs`, `tests/manager-e2e.mjs`.*

**מי רואה מה (החלטת הבעלים):** אדם (הבעלים), אופיר ועירית רואים הכול; ליאור רואה הכול חוץ מכסף; כל השאר רק את מה שעליהם לעשות. הכללים בדפדפן: `app/manager-rules.js`; במסד: `public.is_manager()` (הבעלים, עירית, אופיר) ו־`public.can_archive_clients()` (הבעלים ואופיר).

- **החלפת תצוגה:** לבעלים, לעירית ולאופיר יש בראש כל עמוד (מתחת לסרגל העליון, גם בטלפון) מתג ״המשימות שלי״ / ״מבט מנהל״ (`app/manager-ui.js`, נטען מ־`mountSession` ומעמודי ההצעות). ״מבט מנהל״ פותח את `owner.html`: מסך 1, מסך 2, הטבלה (ולבעלים ולאופיר גם הארכיון). הבחירה נשמרת בדפדפן וקובעת לאן נוחתים בכניסה הבאה (`firstScreenOf` ב־`app/office-ui.js`); בלי בחירה הבעלים נוחת על מבט מנהל, ועירית ואופיר על העבודה שלהם כמו קודם. מסך 1 פתוח עכשיו גם לעירית ולאופיר: במסד הוא כבר היה פתוח להם (`can_ask_questions`, `can_message_clients`, `is_office`), חוץ ממצב הגישות, שהיה תלוי בסימון ״כספת״. `public.access_status_overview()` מחזירה למנהלים רק לקוח, רשת וסטטוס (בלי שם משתמש וסיסמה).

- **מחיקה לצמיתות** (רק מהארכיון; הבעלים ואופיר): `public.purge_client(id, שם)`. דורשת שהלקוח בארכיון ושם העסק מוקלד שוב (במסך גם תיבת ״הבנתי״). נמחקים: הלקוח וכל שורה עם ה־`client_id` שלו בכל טבלה (סימונים, היסטוריה, משימות, שאלות, הודעות, התראות, בקשות שינוי, אישורים, סקרים, דף המצב, הכספת), הסודות שלו ב־Vault (סיסמאות וטוקנים של דף המצב), ורשומות `client_files` אם קיימות. **נשארים:** ההסכם החתום (`quotes`) וההסכמות שלו (`client_consents`), כרשומת המכירה והחתימה. **קבצים ב־Storage לא נמחקים במסד:** אחרי מחיקה, מי שמחזיק את הגישה ל־Supabase מוחק בדלי את הקבצים של הלקוח (ה־id שלו נמצא ביומן).
- **היומן:** `public.client_admin_log` (פעולה, מי, מתי, `client_id`, שם העסק וספירות בלבד; בלי טלפון או פרטים אישיים). אין לו מפתח זר, ולכן הוא נשאר אחרי המחיקה. נקרא בידי הבעלים ואופיר, ונכתב רק בידי הפונקציות.
- **טבלה חדשה עם `client_id`** שנוספת אחרי המיגרציה הזו לא מקבלת לבד את מדיניות הארכיון: מריצים שוב את הבלוק `do $$ … $$` מהמיגרציה (או מוסיפים את המדיניות במיגרציה של הטבלה). המחיקה לצמיתות מוצאת אותה לבד.

**להחלה, בסדר הזה:** המיגרציה ב־SQL Editor; אחריה פרסום האתר (לפני המיגרציה הטבלה מוצגת בלי מחירים והארכיון מחזיר שגיאה); ואחריו פריסה מחדש של `reminders`, `calendar` ו־`whatsapp-webhook` (הן מסננות לפי `archived_at`, שלא קיים לפני המיגרציה). הפריסה של `reminders` ו־`calendar` כוללת את העותק המעודכן `_shared/app/protocol-logic.js`. אין סודות חדשים.
