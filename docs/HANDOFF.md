# מסמך מסירה למפתח: מחולל ההצעות וההסכמים של אסטרטג

המסמך מיועד למפתח שישלב את המערכת במערכת קיימת. הוא מתאר מה נבנה, איפה כל דבר נמצא, מה חייב להישמר בשילוב, ודרכים אפשריות לשלב.

- **קוד:** https://github.com/adamsin155/--- (ענף `claude/amazing-tesla-bvt0sx`; האתר החי מתפרסם מהענף `gh-pages`, רק עם קבצי האתר, ב־`scripts/build-pages.mjs`)
- **אתר חי:** https://adamsin155.github.io/---/
- **שרת:** פרויקט Supabase ‏`czncjzziqrqtezpwxxpz` (Postgres, Auth, Edge Functions)

## 1. מה המערכת עושה

1. איש מכירות מתחבר, בוחר **הצעת מחיר** (לעיון בלבד, בתוקף 48 שעות) או **הסכם התקשרות** (נוסח משפטי + חתימה, ניתן לחתימה 72 שעות).
2. בוחר חבילה, משפיענים, תוספות בתשלום ובחינם, והנחה חודשית של עד 200 ₪. המחיר מחושב מיד.
3. יוצר קישור ללקוח. השרת מחשב את המחיר ואת נוסח ההסכם **מחדש**, ושומר את המסמך כתמונת מצב קפואה עם טביעת SHA-256.
4. הלקוח פותח `q.html?t=<token>`, קורא וחותם (שם, ציור חתימה, תיבת אישור). נשמרים זמן, IP, דפדפן, נוסח האישור וטביעת חתימה. אחרי החתימה השורה ננעלת.
5. הצוות רואה ב־`quotes.html` את כל ההצעות והסטטוסים (ממתין, נצפה, נחתם, פג תוקף, בוטל).

**שלושת הקבצים `catalog.js`, `pricing.js`, `legal.js` הם הלב העסקי.** הם JavaScript טהור (ES modules) בלי תלויות, ורצים גם בדפדפן, גם ב־Node וגם ב־Deno. אפשר לייבא אותם כמו שהם לכל מערכת JS/TS.

מקורות אמת עסקיים: `docs/pricing-rules.md` (כללי תמחור וזכאות), `docs/legal/` (סקירות משפטיות; הנוסח עדיין לאישור עורך דין).

## 3. מודל הנתונים

טבלה `public.quotes` (עיקרי העמודות):

| עמודה | תיאור |
|---|---|
| `id`, `token` | uuid; ה־`token` הוא הסוד בקישור ללקוח |
| `number` | `AST-YYYY-NNNN` |
| `model` | jsonb: כל מה שהלקוח רואה (חבילה, תוספות, סכומים, נוסח משפטי, פרטי לקוח, `validUntil`) |
| `doc_hash` | SHA-256 של `model` (נקבע בטריגר בהכנסה) |
| `status` | `sent` / `signed` / `cancelled` |
| `expires_at` | סוף התוקף (48/72 שעות), נקבע בטריגר |
| `signer_name`, `signature_png`, `signed_at`, `signer_ip`, `signer_user_agent`, `consent_text`, `signature_hash` | ראיות החתימה |
| `monthly_gross_agorot`, `term_gross_agorot`, `client_name`, `created_by_email` | שדות לרשימה |

טבלה `public.staff (email)`: רשימת המורשים. איש צוות = משתמש Auth עם מייל מאושר שמופיע בטבלה.

כל הסכומים **באגורות** (מספרים שלמים). מע״מ 18%.

## 4. ממשקי השרת

| קריאה | מי | מה |
|---|---|---|
| `POST /functions/v1/create-quote` עם `{ selection, client }` | צוות (JWT) | מחשב, שומר, מחזיר `{ id, token, number, created_at }` |
| `rpc get_quote(p_token)` | כל מי שמחזיק בטוקן | מחזיר את המסמך, סטטוס, תוקף וראיות |
| `rpc sign_quote(p_token, p_name, p_signature, p_consent)` | הלקוח (לא צוות) | חותם; נחסם אם פג תוקף, נחתם, בוטל או שזו הצעה לעיון |
| `rpc cancel_quote(p_id)` | צוות | ביטול הצעה שלא נחתמה |
| `select` על `quotes` | צוות (RLS) | רשימה |

דוגמת `selection`:

```json
{ "docType": "agreement", "tier": "social-tv", "influencer": "natali",
  "paid": ["photographer", "natali-reel"],
  "free": { "graphics": 0, "simeonStories": 0, "simeonJoin": false, "extraCh14": false },
  "discount": 20000 }
```

## 5. מה חייב להישמר בשילוב

1. **המחיר ונוסח ההסכם מחושבים בשרת בלבד.** לא לקבל סכומים או נוסח מהדפדפן.
2. **מסמך שנוצר לא משתנה.** שינוי = הצעה חדשה. שינוי עתידי ב־`legal.js` לא ישפיע על מסמכים קיימים, כי הנוסח שמור ב־`model`.
3. **ראיות החתימה** נשמרות כמו שהן (כולל נוסח האישור המדויק והטביעות), ואיש צוות לא יכול לחתום בשם לקוח.
4. **תוקף** נאכף בשרת (לא רק בתצוגה).
5. **כל שינוי בחבילות או בנוסח** עובר דרך `catalog.js`/`legal.js` + `npm test`, ואז פריסה מחדש של `create-quote`.

## 6. דרכים לשלב

בחירה בין הדרכים תלויה במערכת הקיימת (שפה, מסד נתונים, התחברות משתמשים).

**א. להשאיר כמערכת נפרדת ולקשר אליה (הכי מהיר).**
קישור מהמערכת הקיימת ל־`index.html`, ואפשר להעביר פרטי לקוח בפרמטרים. מתאים אם לא צריך את הנתונים בתוך המערכת הקיימת.

**ב. המערכת הקיימת קוראת לשרת הזה (API).**
המערכת הקיימת קוראת ל־`create-quote` (למשל מכרטיס לקוח ב־CRM), שומרת את `number` ו־`token`, ומושכת סטטוסים. אפשר להוסיף Database Webhook על `status = 'signed'` שמודיע למערכת הקיימת על חתימה. צריך לסגור איך משתמשי המערכת הקיימת מקבלים JWT של צוות (משתמש שירות ייעודי או SSO).

**ג. להעביר את הלוגיקה למערכת הקיימת.**
לייבא את `catalog.js`, `pricing.js`, `legal.js` (בלי שינוי) ואת `quote-doc.js` לרינדור. להעתיק את הסכמה, הטריגרים וה־RPC מ־`supabase/migrations/` למסד הנתונים הקיים (Postgres) או לממש את אותם כללים בשכבת השרת הקיימת. לנייד את ההצעות הקיימות (`AST-2026-0001` ואילך) יחד עם `doc_hash` וראיות החתימה, בלי לשנות אותן.

**ד. להטמיע את הממשק.**
העמודים סטטיים ואפשר להטמיע אותם ב־iframe או להעביר את הרכיבים למסגרת של המערכת הקיימת (React וכו׳). העיצוב ב־`app/styles/`, והגופנים מקומיים ב־`app/fonts/` (Rubik, JetBrains Mono).

## 7. הרצה מקומית

```bash
npm install
npm test                                   # 22 בדיקות מנוע
npx http-server -p 8080 . &                # אתר מקומי
node tests/e2e.mjs                         # 27 בדיקות דפדפן מול Supabase מדומה
```

פריסת הפונקציה: `node scripts/sync-functions.mjs` ואז `supabase functions deploy create-quote`. הפונקציה מייבאת עותק של `app/*.js` מ־`supabase/functions/_shared/app/`, שנוצר בסקריפט. הפירוט ב־[מדריך התפעול](ops.md).

## 8. גישות שבעל המערכת צריך לתת

- **GitHub:** הזמנה כ־collaborator למאגר (או fork).
- **Supabase:** הזמנה לארגון בלוח הבקרה (Organization → Team). מפתחות סודיים (service role, סיסמת מסד הנתונים) נמסרים רק משם, לא בצ׳אט או במייל.
- **שים לב:** המאגר ציבורי כרגע. אם השילוב יכלול קוד פנימי או סודות, להפוך אותו לפרטי קודם.

## 9. פתוח / לא נבנה עדיין

- שליחת מייל אוטומטית: התראה לצוות על חתימה ועותק חתום ללקוח (דורש ספק מייל, למשל Resend).
- שכפול הצעה קיימת לעריכה.
- PDF שמופק בשרת (כרגע הדפסה מהדפדפן).
- יומן אירועים שאי אפשר לשנות, גיבוי מחוץ ל־Supabase, אימות דו־שלבי לצוות.
- הנוסח המשפטי ממתין לאישור עורך דין; ערכי ברירת מחדל ב־`TERMS` ב־`app/legal.js` (50% ביציאה מוקדמת, תקרת אחריות 6 חודשים וכו׳) ממתינים לאישור בעל המערכת.
